# B 站原生图文结构核验

核验日期：2026-11-11。这里只记录公开前端代码中的格式，没有访问用户 Cookie，没有调用上传、保存或发布接口。

## 一手来源

- 当前编辑器入口：https://member.bilibili.com/york/read-editor
- 从入口 HTML 实际引用的当前 JS：https://s1.hdslb.com/bfs/static/sunflower/read-editor/assets/index-iVnxuzkp.js
- 参考实现：https://github.com/wechatsync/Wechatsync/blob/42f61e39e214b8d5377d09d788a716defc4abdc0/packages/core/src/adapters/platforms/bilibili.ts

当前 B 站前端版本常量为 `eva3-4.0.0`。Wechatsync 参考实现仍调用旧 HTML 草稿接口，新插件使用当前页面的原生 Opus 结构，不依赖旧 HTML 在新编辑器中被隐式转换。

## 已核实的当前草稿行为

- 保存：`POST /x/dynamic/feed/article/draft/add`，JSON 数据中 `arg` 包含草稿对象。
- 读取：`GET /x/dynamic/feed/article/draft/view?article_id=...`，响应内容位于 `data.draft`。
- 草稿的 `original` 是原创声明布尔值转成的 0/1；`reprint` 是另一项转载选项，不能用它替代原创声明。
- 文集使用 `list_id`，编辑器读取返回的 `draft.list.id`。
- 自定义封面使用 `image_urls: [url]`；编辑器将第一张图读入封面状态，并以封面状态是否为空初始化自定义封面开关。
- `opus` 包含 `opus_source: 2`、`title`、`content`、`pub_info.editor_version`、`attachments`。
- 正文 `content` 是 `{ paragraphs: [...] }`。

## 正文节点

| 内容 | 当前前端对应结构 |
| --- | --- |
| 普通段落 | `para_type: 1`，`text.nodes` |
| 图片段落 | `para_type: 2`，`pic.pics` 图片数组，`pic.style: 0` |
| 分割线 | `para_type: 3`，`line.line_type: 1` |
| 引用段落 | `para_type: 4`，`text.nodes` |
| 有序/无序列表 | `para_type: 5/6`，`format.list_format`，连续分组使用 `format.combine_hash` |
| 代码 | `para_type: 8`，`code.lang`、`code.content` |
| 标题 | `para_type: 9`，`format.heading_type`、字词的 `font_size` 和 `font_level` |
| 普通文字 | `node_type: 1`，`word.words`、`font_size`、`font_level`、`color`、`dark_color`、`style` |
| 行内公式 | `node_type: 5`，`formula.latex_content` |

文字 `style` 明确支持 `bold`、`italic`、`strikethrough`、`underline`。颜色是字符串，当前前端直接传递文本颜色值；背景色通过 `word.bg_style` 中的 `style:1`、`color` 对象表示。图片字段为 `url`、`width`、`height`、`size`，可含 `comment`。图片大小保留上传 API 返回的量纲，不自行将其替换成文件字节数。

当前普通文字节点没有原生上标/下标字段。插件把上下标连同相邻的拉丁/希腊字母基底组合为可编辑的行内 LaTeX，而不是替换为看起来相似的 Unicode 字符。带 `data-formula`/`data-latex` 的微信 SVG 公式使用其已有源码，并只转换最外层公式节点，避免 SVG 内部文字重复。

## 验证范围与限制

接口字段和节点结构来自当前代码，不能代替实际保存、重新打开和页面渲染的端到端测试。服务器可能额外限制文件格式、尺寸、公式命令或颜色；插件必须检查 API 结果和保存读回结果，失败时保留编辑内容。

当前结构中没有核实通用行内位图节点。没有 LaTeX 源码的行内公式图片、行内微信表情不能直接挪到独立段落而宣称无损。转换器会返回阻断问题，交由用户明确处理或由上层针对该局部进行保真图片回退。CSS 背景、复杂表格等不属于上述普通原生结构。

本地测试文章的结构检查发现：正经玩正文尾部含一个 `Yellowdog.png` 微信狗头表情，和文字在同一行。其余四篇的普通正文均可转换；含 CSS 背景图的区块由上层局部转图处理。结构测试使用模拟上传后元数据；真实验证记录见下文。

## 最终本地结构集成回归

`tests/real-opus.test.js` 对用户保存的五份 HTML 运行真实文章清理、真实局部转换目标选择，以模拟完成的图片替代这些目标，并提供模拟上传结果后，运行真实 Opus 转换器。五篇均无原生结构阻断。该测试不进行截图、不验证截图像素，不发送网络请求，也不保存或发布真实草稿。

## 2026-11-11 Edge 真实导入

用户在扩展面板选择保存的「手机的清晰度 | 正经玩」HTML 及配套资源后，实际完成图片上传和草稿保存。重新打开 B站原生编辑器，确认 16 个正文图片节点均加载，GIF 的显示地址仍为 GIF，4 个源公式与 7 处下标可见，蓝色加粗文字保留。封面开关开启并显示源文章封面，原创已勾选，文集为「正经玩」。没有发布。

B站读回结果存在两项格式归一化：自定义封面保持 `/bfs/new_dyn/` 资源路径，但域名由 `i0.hdslb.com` 改为 `article.biliimg.com`；文字段落增加空 `format.indent` 对象。以完整 URL 和原始对象逐字比较会产生误报。校验需识别这些已观察到的等价形式，同时保持对图片路径、顺序、尺寸、文字、颜色、公式和实际缩进变化的检测。

首次真实回读另发现实际差异：10 个文字节点的源字号被服务器改为 17，不能当作等价归一化。三处黑字（实验器材、实验步骤、原理解说）补上 `bili_theme:Ba0`，该主题明暗均为黑色，与原始黑色等价；不是白字变黑。0.1.1 调整字号档位映射，旧草稿保留作为问题复现依据。

同日重新加载后，再次从同一份本地网页导入，新草稿的保存回读核对通过，插件自动打开草稿。网页验证 16 个图片节点（1 个 GIF）与 11 个公式节点全部加载；「实验步骤」「原理解说」以原生 H3 呈现；封面、原创与「正经玩」文集正确。该验证说明新版导入数据符合转换后的原生档位，不表示源任意字号逐像素不变。

### 字号和主题颜色的修正规则

官方 `index-iVnxuzkp.js` 中，当前编辑器配置明确为 `fontSize:false`、`fontLevel:undefined`；`FontLevel` 默认仅开放正文 `small=13px` 和 `regular=17px`。官方 HTML 导入按最近档位选取，15px 中点归到 17px。插件因此把正文 14px 转为 13px、16px 转为 17px；混合字号段落内的 20/24px 也只能归到 17px，并汇总成一次明确提示，不能继续用任意 `font_size` 值宣称原生保留。

`HEADING_STYLES` 与 `detectHeadingLevel` 证实整段标题有 `24/xxLarge`、`22/xLarge`、`20/large` 三档。插件对每个已经分开的段落单独判断：仅当可见文字字号一致且整段为 20/22/24px 时使用对应标题，不合并段落，不把引用或列表变成标题。H4–H6 不能依据旧常量误认作额外原生字号。当前包的内置 CSS 又将 h1/h2/h3 显示为 19/18/17px，并设字重与段间距，所以这里只保证使用原生标题档位，不承诺显示像素尺寸与源页面完全一致；提示中明确由 B站控制实际字号、字重和段间距。

官方 `colorToString` 优先使用主题变量而非 `colorValue`，因此错误的主题不能忽略。`Wh0` 的官方明暗配对为 `#FFFFFF` / `#17181A`，`Ba0` 为黑 / 黑。插件对白色正文和背景显式使用 `Wh0` 及其暗色配对，保留浅色模式的白色并遵循 B站暗色主题；其它颜色不作近似调色板映射。这是依据公开代码的预防性处理，现有样稿实测没有发生白字变黑。

上述早期实测采用本地文件导入。随后 0.1.4 已由用户发起直接微信链接导入并完成保存回读，细节见 docs/validation-v0.1.4.md。其余四篇仍为本地结构回归。网页截图保存在项目 `test-artifacts/live-formulas.jpg` 与 `test-artifacts/live-settings.jpg`，不进入发布 ZIP。

## 原生图片注释（0.1.5）

官方图片节点的 `pic.pics[].comment` 对应编辑器中的「图片注释」。公开 bundle 的 `getImageCaptionFromElement`（字符偏移 1771323）读取 `data-caption` 或最近 figure 下的 figcaption；`CaptionManager` 与 `normalizeImageCaption` 将文本限制为 100 个 JavaScript UTF-16 代码单元，且不支持换行和富文本。

插件把确认的一图一图注映射到该字段，保留同一图片的关联并消除正文重复。超长、公式/上下标、强调或彩色图注保留为下方原生正文并提示，不借平台截断实现导入。普通灰色小字采用平台图注样式。保存回读同时检查图注文字和所属图片。五篇本地转换产生的原生图注数分别为 1、3、4、9、19；问答另一处蓝色图注保留正文颜色。

同日在真实 B站草稿中通过原生界面填入正经玩的四条图片注释，保存并重新打开确认仍与图片 0、3（GIF）、12、13 对应，16 个图片及 11 个公式保留，重复文字段落已移除。重新读取可见 DOM 后，其剩余正文文字与本地原生转换结果完全一致。此项验证证明原生注释可保存显示，不等同于尚未重载的 0.1.5 自动导入流程验收。
